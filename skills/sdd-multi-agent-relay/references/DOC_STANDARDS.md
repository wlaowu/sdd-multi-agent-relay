# 方案 / 计划 / 任务文档整理标准与配模指南（DOC_STANDARDS）

本标准旨在消除人类、方案中枢（`Hub`）、分发中枢（`Codex-Hub`）、实施专席（`AB`）与独立审计（`R0`）之间的语义落差——用统一结构、全链路编号与可量化验收，实现**“输入一次清晰方案，后续持续自动推进少返修”**。

---

## §1 用户极简提需求入口（日常只需说这几句）

平时提新需求或启动长任务，**不需要自己手写长文档**，只需套用下面 4 种口令：

### 1. 立项整理方案（新需求起步）
> 「用 `sdd-multi-agent-relay` 流程立项：
> 1. **想做什么**：……
> 2. **在哪用／给谁用**：……
> 3. **最怕出什么错**：……
> 4. **做到什么样算达标**：……
> 请按《文档整理标准》先整理出完整 Spec（含 `V-xx` 验收矩阵与 `PD-xx` 待拍板项），别急着改代码。」

### 2. 预审并收敛决策（复杂 L3 任务推荐）
> 「先拉 `R0` 对这份方案做一次实施前设计预审，按阻塞风险补充反例，把需要我拍板的项收敛成 `PD-01..` 清单。」

### 3. 拍板并一键开启无人值守（唯一一次人工授权）
> 「我确认定稿，拍板结论：`PD-01=...`、`PD-02=...`。按 `L3` 全程自动续推（通过即派下一阶段，最多返修 2 轮，遇熔断/阻塞停止并通知我；全部完成后按配置汇报／关机）。请转交给 `Codex-Hub` 拆阶段并开跑。」

### 4. 中途改需求（Mid-Flight CR）或重启续跑
> - 中途变更：「暂停当前自动派单，发起 Spec 变更（CR）：把……改为……。请按 `CR_DELTA.md.template` 整理增量提案与受影响 `V-xx`，更新方案版本号并同步看板再继续。」
> - 断点恢复：「按 `sdd-multi-agent-relay` 断点恢复协议检查当前项目进度并继续托管推进。」

## §2 方案文档整理标准（`specs/<THEME>_SPEC_V0.x.md` — 解决「做对事」）

配套模板：[SPEC.md.template](../resources/SPEC.md.template) 与增量变更模板 [CR_DELTA.md.template](../resources/CR_DELTA.md.template)；端到端参考范本见 [examples/sample-pkg/](../examples/sample-pkg/)。每份达到可批准开工标准的 Spec **必须齐备 8 个板块**：

| 序号 | 必填板块 | 核心作用与写法要求 |
| --- | --- | --- |
| **1** | **文档头与效力标签** | 标明版本号、对照 Git 基线 SHA、版本变更摘要与 5 选 1 效力标签（`[讨论草案·未授权实施]` / `[设计预审·待拍板]` / `[已批准方案·本次执行依据]`）。 |
| **2** | **目标与「显式非目标」（Goals & Non-Goals）** | 既列“本轮做什么”，更硬性列“**本轮明确不做什么**”，防止 AI 过度设计、重构无关代码或偷跑下一阶段。 |
| **3** | **核心业务规则与不变量（Invariants）** | 用可判定的陈述句写死业务底线（如“同指纹请求重复触发 0 次二次计费”“迟到响应只写历史不覆盖当前版本”）。 |
| **4** | **数据模型与接口契约** | 数据结构字段、存储隔离/旧版迁移策略、API/IPC 入参出参及显式错误码分类（区分内部排查码与安全对客原因）。 |
| **5** | **异常边界与极端反例（Failure Modes）** | 每条核心路径至少列 2～3 个极端坏情况及兜底（断连、关窗/取消、重复点击、非法输入、外部服务超时），直接转化为 `AB` 单测与 `R0` 必查项。 |
| **6** | **分层验收矩阵（`V-01`～`V-xx`）** | 逐条写明验证层级（`离线单测` / `合成 Mock` / `真机实测`）、操作步骤与**可量化判定值**（如退出码 `0`、精确字节/帧/次数）。 |
| **7** | **安全、写锁与保密红线** | 明确权限边界、禁止读取/透传 API Key 或私密媒体、禁止未授权付费请求。 |
| **8** | **待拍板决策表（`PD-01`～`PD-xx`）** | 所有含糊二选一集中在此；**必须全部转为明确决策并移除草稿标签后，方案才算可施工依据**。 |

## §3 执行计划整理标准（`Plan` / `DISPATCH_BOARD.md` — 解决「怎么切步」）

由 `Codex-Hub` 据已批准方案拆解，须满足 6 条硬标准：
1. **单阶段尺寸可控**：避免过度碎片化拆单导致频繁接力与冷编译，优先合并为 **2～3 个清晰垂直大阶段**（中小独立需求优先走 `L2` 快车道 1 次终审）；中间阶段只跑**受影响模块定向快测 + Red→Green 反例**，全量重型 E2E 留到收官里程碑跑 1 次。
2. **波次（Wave）依赖清晰**：看板阶段任务总表配备 `波次/依赖` 列（`W0`、`W1`、`W2（依赖 T-01）`…），按 `底座 → 核心模块（无依赖同波次可多 Worktree 并行） → 跨端终局集成` 排布；每阶段完成即打轻量门禁 Tag（`gate/<batch>-<stage>-pass`）。
3. **写死准出门禁（Gate）**：标明阶段必过哪几条 `V-xx`、需要 `0` 个阻塞/高危发现，才能解锁下一阶段。
4. **前置里程碑真机门禁（`C` 专席）**：明确标注哪几个关键阶段完成后须唤醒 `C` 做真实 OS / GUI / 硬件冒烟测试，不把真机兼容性雷区拖到终点。
5. **遗留项显式承接**：明确列出上一阶段 `R0` 遗留的低危或观察项（如 `R0-T01-03`）在本阶段还是 `C` 阶段关闭，严禁静默丢弃。
6. **开工前防漂移体检与上下文预算守恒**：派单开工前跑通 `relay.mjs analyze --json`（确保 `V-xx` 齐备、无未决 `PD-xx`、无重号/缺标签/断链）；看板/状态/任务卡保持在 `contextBudgets`（默认 `160` / `120` / `250` 行）内，超长时使用 `relay.mjs compact --apply` 归档历史调度日志。

### §3.1 强制任务编号规范（所有任务末尾必带编号）

为确保全链路讨论、看板、提交、审计与复盘可精准对齐，所有任务和派生单据必须遵守统一编号规则（**顺序递增、永不复用**）：

| 类别 | 格式规范 | 示例 | 使用位置 |
| --- | :--- | :--- | :--- |
| **实施前预审** | 固定 `T-00` | `方案定稿与实施前独立预审 [T-00]` | 看板总表、预审报告 |
| **主任务编号** | `T-01`、`T-02`、`T-03`… | `底座与安全 [T-01]`、`核心功能 [T-02]` | Spec 草案、看板、任务卡标题末尾 `[T-xx]` |
| **拆分子任务** | `T-xx.1`、`T-xx.2` | `接口契约定义 [T-01.1]` | 复杂阶段内部拆分 |
| **独立审计单** | `T-xx-R0` / `T-xx-FIX1-R0` | `T-01-R0`、`T-01-FIX1-R0` | 看板、`tasks/R0-review.md` |
| **定向返修单** | `T-xx-FIX1`、`T-xx-FIX2` | `T-01-FIX1`、`T-01-FIX2` | `AB` 返修任务卡（最多 2 轮） |
| **真机里程碑** | `T-xx-C` | `Windows 真机验收 [T-02-C]` | 看板、`tasks/C-desktop.md` |
| **审计缺陷号** | `R0-Txx-01`、`R0-Txx-02` | `R0-T01-01` | `audits/`、`ISSUE_LEDGER.md` |
| **Git 提交与 Tag** | `feat(T-01): ...` / `gate/<batch>-T-01-pass` | `feat(T-01): ...`、`fix(T-01-FIX1): ...` | Git Commit、门禁 Tag |

> **硬性格式约定**：任务卡、看板行与阶段标题中的**每个任务名称末尾均须附带 `[T-xx]`**（如 `数据迁移与防重底座 [T-01]`）；独立「任务编号」列填写纯 `T-01` 便于检索和脚本识别。

## §4 任务卡整理标准（`tasks/*.md` — 解决「怎么交接」）

采用固定三段式，各写各区、严禁混写或代填：
1. **派发区（仅 `Codex-Hub` 写，完整模板见 [ROLE_PROMPTS.md](./ROLE_PROMPTS.md)）**：
   - 标准 **8 字段首部**（`发送到`、`发送方`、`接收会话`、`任务编号`、`任务名称 [<T-xx>]`、`所属批次`、`发送时机`、`投递状态`），明确**谁发、谁做、做到什么编号**；
   - 任务章节标题按 `## <任务名称> [T-xx]` 命名，并标明固定对象（基线 40 位 SHA）、**所属波次**与写锁范围；
   - **随单文档包（Context Pack）**：3–8 条摘要 + 精确路径/章节/SHA-256 + 效力标签；
   - **本单范围、显式禁越界清单** + **Red → Green TDD 必交证据要求** + 必跑验证命令、反例计数与回执/分流路径。
2. **接棒回执（仅 `AB`/`C` 开工写，≤ 5 行）**：标明任务编号 `T-xx`，核对基准 SHA、随单指纹、领取限本单写锁。
3. **执行回执（仅 `AB`/`C` 完工写）**：
   - 冻结 40 位 Git SHA（提交信息带 `feat(T-xx):` 或 `fix(T-xx-FIX1):`）与唯一父提交；
   - **Red → Green TDD 实测证据**（先编写必失败边界/反例测试的 Red 失败日志 + 实现后全部转绿的 Green 通过日志）；
   - 交付摘要 + 对照前序 `R0-Txx-xx` 问题关闭情况；
   - 真实执行命令与退出码 + 证据清单 `SHA256SUMS` 与关键反例计数；
   - **明确分开列「已在本环境验证」与「未验项及后续责任归属」**。

## §5 拉高默契的 2 条写作铁律

1. **全链路编号贯通**：需求决策用 `PD-01`，方案验收用 `V-01`，任务用 `T-01`（标题后缀 `[T-01]`），审计缺陷用 `R0-T01-01`，返修回执与 Git 提交全部对齐同一任务号，一句“关闭 `R0-T01-02` 并放行 `T-02`”绝无歧义。
2. **禁用模糊形容词，一律翻译成可观测行为**：

| 模糊说法（禁止出现在 Spec/Task） | 可执行、可审计写法（标准范式） |
| --- | --- |
| “界面自适应，交互友好” | “视口 `< 1280px` 折叠侧栏且横向零溢出；主要操作按钮桌面键盘 `Tab/Enter` 可达” |
| “报错提示清晰” | “映射为枚举化的业务安全原因码 + 中文引导文案，不透传底层堆栈、绝对路径或环境变量值” |
| “防止重复提交/扣费” | “同请求指纹在未获确定终态前保持受理锁，重复点击产生 `0` 次外部 POST” |
| “尽量快一点、性能好一点” | “列表翻页采用按需 IPC 分页限额（每页 ≤ 50 条），零后台固定周期轮询” |

## §6 Antigravity 按角色分层配模指南

为兼顾**深水区严谨度**与**通宵巡检不断档**，Antigravity 会话建议按角色分层配模，禁止所有会话无差别挤占单一稀缺配额：

| Antigravity 角色 | 任务特征 | 推荐模型档位 | 核心考量 |
| --- | --- | :--- | :--- |
| **第 0 层：总控中继主会话** | 每 3 分钟巡检一次脚本状态与简单规则分流 | **规划+执行双模（如 Orchestrator）或额度充裕的均衡模型** | 巡检频次高但逻辑简单，避免被高消耗慢模型拖垮或巡检耗尽主额度 |
| **`Hub` 方案与复盘专席** | 低频次、高杠杆（立项 / 熔断复盘 / Spec 变更） | **顶配推理与规划模型（`pro` 档）** | 方案阶段多算一分深度，能省掉后面几轮代码大返修 |
| **`R0` 独立审计专席** | 低频高深（预审排雷 + 逐阶段审冻结 SHA 代码） | **高严谨度代码分析强模型（`pro` 档）** | Codex 写代码 + Antigravity 强模型审代码构成**跨模型家族交叉评审**；若旧审计子会话遇 `429`，立即**新建**独立 `R0` 子会话而非死等 |
| **资料调研 / 浏览器验证等辅助** | 高并发轻量交互 | **轻量快速档（`flash` / `flash_lite`）** | 速度快、低延迟、零额度压力 |
